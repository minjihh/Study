## 1. 핵심 정리

### 1-1. 타입 힌트와 TypedDict (lg01)
| 코드 | 의미 | 강제성 |
|---|---|---|
| `sample_dict: Dict[str, str] = {...}` | "키도 값도 str인 dict"라고 **사람/에디터에게 알려줌** | **없음**. `'age': 39`(int)를 넣어도 실행 에러 안 남 |
| `class Person(TypedDict): name: str; age: int; job: str` | **키 이름과 각 값의 타입이 정해진 dict**의 설계도 | 역시 **실행 시 검사 없음** (mypy, Pylance 같은 정적 검사기만 경고) |
| `Person(name='홍길동', age=40, job='도적')` | 클래스처럼 호출하지만 **결과는 그냥 `dict`** | `type(person)` → `<class 'dict'>` |
| `person2: Person = {...}` | dict 리터럴에 타입 힌트만 붙인 것 | 위와 동일한 dict |

- 출력: `{'name': '홍길동', 'age': 40, 'job': '도적'}` (객체가 아니라 dict 모양 그대로 출력)
- `sample_dict`의 `'age': '39'`는 **문자열** `'39'`. `Dict[str, str]`라서 일부러 str로 적은 것.
- 접근은 **`person['name']`** (dict처럼). `person.name`은 `AttributeError`. (점(.) 접근은 dataclass/pydantic 방식)
- **왜 LangGraph에서 쓰나?** 그래프 전체가 공유하는 State의 "키 목록과 타입"을 선언하는 용도. `StateGraph(State)`가 이 선언을 보고 **각 키를 어떻게 갱신할지**(덮어쓰기 or 리듀서) 결정함.

### 1-2. Reducer: `Annotated[list, add_messages]` (lg02)
```python
class MyDate(TypedDict):          # (오타: MyData 의도로 보임. 코드에서 실제로 쓰이진 않음)
    messages: Annotated[list, add_messages]
```
- `Annotated[타입, 추가정보]`: 타입은 `list`, 추가정보로 **"이 키는 `add_messages`로 합쳐라"** 를 붙임.
- 노드가 `{'messages': [새 메시지]}`를 반환하면 → `add_messages(기존 리스트, 새 리스트)` 결과가 새 State가 됨.

| 상황 | 결과 |
|---|---|
| `add_messages([Human('안녕', id='1')], [AI('방가', id='2')])` | **2개**: 뒤에 이어 붙임 (append) |
| `add_messages([Human('안녕', id='3')], [AI('방가', id='3')])` | **1개**: 같은 id → **덮어쓰기** → `[AIMessage('방가', id='3')]`만 남음 |
| id 없는 메시지 | `add_messages`가 **고유 id(uuid)를 자동 부여** 후 이어 붙임 → 평소엔 계속 쌓임 |
| `("user", "질문")` 같은 튜플 | `HumanMessage`로 **자동 변환**됨 (lg03의 `invoke` 입력이 이 형식) |

- 리듀서가 **없는** 키(예: `aaa: str`)는 노드가 반환하면 **그냥 덮어쓰기**.
- import 경로: lg02는 `from langgraph.graph import add_messages`, lg03은 `from langgraph.graph.message import add_messages`. **둘 다 같은 함수**(원래 위치는 `langgraph.graph.message`).

### 1-3. 첫 LangGraph 챗봇: 6단계 (lg03)
| 단계 | 코드 | Keras 비유 (코드 주석) |
|---|---|---|
| 1. State 정의 | `class State(TypedDict): messages: Annotated[list, add_messages]; aaa: str; ...` | 데이터 모양 정하기 |
| 2. Node 정의 | `def chatbot(state): return {'messages': [llm.invoke(state['messages'])]}` | 레이어 하나 = 함수 하나 |
| 3. 그래프 구성 | `graph_01 = StateGraph(State)` → `add_node("chatbot", chatbot)` | `model = Sequential()` → `model.add(...)` |
| 4. Edge 추가 | `add_edge(START, "chatbot")`, `add_edge("chatbot", END)` | 레이어 연결 순서 |
| 5. 컴파일 | `graph = graph_01.compile()` | `model.compile()` |
| 6. 실행 | `graph.invoke({"messages": [("user", query)]})` | `model.predict()` |

- **Node 규칙**: State를 받아서 **바꾸고 싶은 키만 담은 dict**를 반환. 전체 State를 반환할 필요 없음.
- `llm.invoke(리스트)` → `AIMessage` **하나**를 반환. 그래서 `[ ]`로 감싸서 리스트로 만들어 반환 → 리듀서가 이어 붙임.
- 실행 결과 `response`도 dict: `response["messages"]` = `[HumanMessage, AIMessage]`
  - `response["messages"][0].type` → `'human'`, `[1].type` → `'ai'`, `[1].content` → 답변 텍스트
- `aaa`, `bbb`, `ccc`는 **선언만 하고 아무도 값을 안 넣음** → invoke 결과에 **이 키들은 아예 없음**(`response['aaa']` → `KeyError`). TypedDict 키는 "필수 입력"이 아님.
- `compile()` 전의 `graph_01`(StateGraph 빌더)에는 `invoke`가 없음 → 반드시 compile한 `graph`로 실행.
- 질문 `"삼성전자의 주가를 예측해줘"`: 이 챗봇엔 **검색 도구가 없음** → LLM은 학습 데이터만으로 답하므로 "실시간 정보 없음/예측 불가" 류의 답이 정상. (이 한계를 10-21 수업에서 ToolNode + 검색으로 해결)

### 1-4. 노드 여러 개 일렬 연결 (lg04)
```
START → prepare → chatbot → finish → END
```
| 노드 | 반환 | 하는 일 |
|---|---|---|
| `prepare` | `AIMessage("질문을 접수했습니다.")` | LLM 호출 없이 **고정 메시지**만 추가 |
| `chatbot` | `llm.invoke(state["messages"])` | 이때 LLM은 `[Human 질문, AI "질문을 접수했습니다."]` **2개**를 보고 답함 |
| `finish` | `AIMessage("답변 처리가 완료되었습니다.")` | 마무리 고정 메시지 추가 |

최종 출력 (`for i, msg in enumerate(response['messages'])`):
```
[0] human : 삼성전자의 주가를 예측해줘
[1] ai : 질문을 접수했습니다.
[2] ai : (LLM 답변)
[3] ai : 답변 처리가 완료되었습니다.
```
- 메시지가 **4개**인 이유: 입력 1 + 노드 3개가 각각 1개씩 추가 (리듀서 덕분에 덮어쓰지 않음).
- 노드 함수 이름과 `add_node`의 **문자열 이름**은 달라도 됨. 엣지는 **문자열 이름** 기준으로 연결.
- `add_node`만 하고 엣지를 빼먹으면(예: `finish → END` 없음) compile 단계에서 **도달 불가/끝나지 않는 노드** 관련 에러나 경고가 남. 노드는 반드시 START에서 END까지 이어져야 함.

### 1-5. 코드에서 눈여겨볼 점
1. **API 키 관리**: `load_dotenv()` → `os.environ["MONOROUTER_API_KEY"].strip()`. 키를 코드에 직접 쓰지 않고 `.env`에 둠. `.strip()`은 줄바꿈/공백 섞인 키 때문에 인증이 실패하는 것을 막음. **`.env`는 절대 커밋 금지** (`.gitignore` 확인).
2. **`base_url`**: OpenAI 공식이 아닌 **OpenAI 호환 라우터**(monorouter)를 쓰므로 `ChatOpenAI`에 `base_url`을 같이 줌 (코드 주석: "openAI와 달리 url도 같이 입력").
3. `os.environ["KEY"]`는 키가 없으면 **`KeyError`**, `os.getenv("KEY")`는 **`None`** 반환 → 그 상태로 `.strip()`하면 `AttributeError`.
4. `temperature=0`: 같은 질문에 최대한 같은 답. 단, 일부 추론형(reasoning) 모델은 temperature를 지원하지 않거나 `max_tokens` 안에 **내부 추론 토큰까지 포함**돼 답이 비거나 잘릴 수 있음 → 답이 비면 `max_tokens`를 늘려볼 것.
5. lg04에서 chatbot이 받는 메시지의 **마지막이 AI 메시지**("질문을 접수했습니다."). 대부분 문제없이 동작하지만, 모델에 따라 "이미 답한 상태"로 여겨 답이 짧아질 수 있음. 안내용 고정 메시지는 State의 **다른 키**(예: `aaa`)에 넣는 설계도 가능.

### E (모범 답안 요지)
1. 리듀서 = **"기존 값과 새 값을 어떻게 합칠지" 정하는 함수**. LangGraph는 노드가 반환한 값을 State에 반영할 때, 리듀서가 없으면 덮어쓰고 있으면 `리듀서(기존, 새값)`으로 합침. 챗봇은 사람 질문 → AI 답변 → (도구 결과) → ... 처럼 **대화 기록이 쌓여야** LLM이 맥락을 보고 답할 수 있으므로, `add_messages`로 이어 붙여야 함. 없으면 매 노드마다 이전 메시지가 사라짐 (C4 참고). 또 id가 같으면 교체하는 기능 덕분에 메시지 수정도 가능.
2. State 정의 ≈ 입력/출력 데이터 모양 정하기, Node ≈ 레이어(각각 한 가지 일을 하는 함수), `StateGraph(State)` ≈ `Sequential()`, `add_node` ≈ `model.add`, `add_edge` ≈ 레이어 연결 순서(Functional API에서 `x = Layer()(x)`로 잇는 것에 더 가까움), `compile()` ≈ `model.compile()`, `invoke()` ≈ `model.predict()`. 차이점: LangGraph는 조건 분기/루프가 가능하고, "학습"이 아니라 **실행 흐름**을 정의함.
3. lg03은 도구 없이 LLM만 호출 → LLM은 **학습 시점까지의 지식**만 있고 실시간 주가를 모름 (또 주가 "예측"은 원래 확정적으로 답할 수 없는 질문). 10-21 수업에서 `TavilySearch`/`DuckDuckGoSearchRun` 검색 도구를 `bind_tools`로 알려주고, `ToolNode` + `tools_condition` + `tools → chatbot` 루프로 **필요하면 웹 검색 후 답하는** 구조로 보완함.

## 📌 오늘의 체크리스트
- [ ] `TypedDict`는 "키/타입 설계도"일 뿐 실행 시 검사하지 않는다는 걸 안다
- [ ] `add_messages`: id 다르면 이어 붙이기, id 같으면 교체, 이 두 동작을 예측할 수 있다
- [ ] 노드는 **바꿀 키만** dict로 반환한다는 규칙을 안다
- [ ] State → Node → StateGraph → Edge(START/END) → compile → invoke 6단계를 안 보고 쓸 수 있다
- [ ] lg04 출력이 왜 4줄인지 설명할 수 있다
- [ ] 리듀서를 빼면 결과가 어떻게 달라지는지 말할 수 있다
