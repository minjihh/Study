## 2. 🏁 대회 제출 파이프라인 (`keras13`, `keras14`, `keras22`, `keras24`)

### 2-1. 표준 흐름 (따릉이 `keras13_ddarung02_submit.py`)
```
read_csv(train/test/submission, index_col=0)
 → 결측치 처리 (train: dropna / test: fillna)
 → x = train.drop(['count'], axis=1), y = train['count']
 → train_test_split  →  fit  →  evaluate(x_test)  →  RMSE
 → y_submit = model.predict(test_csv)
 → submission['count'] = y_submit  →  submission.to_csv(...)
```
- `index_col=0`: 첫 컬럼(id)을 **인덱스로** 써서 학습 데이터에서 빠지게 합니다. 빠뜨리면 id가 피처로 들어가 `input_dim`이 1 늘어납니다.
- shape: train `(1459, 10)`(count 포함), test `(715, 9)`, submission `(715, 1)`. **test에는 정답 열이 없습니다.**
- 결측치 처리를 다르게 하는 이유
  - **train**은 행을 지워도 됩니다(`dropna`, 1459행 → 1328행).
  - **test**는 **절대 행을 지우면 안 됩니다.** submission이 715행을 그대로 요구하므로 `fillna(test_csv.mean())`로 채웁니다.
  - 더 정석은 **train의 평균**으로 채우는 것입니다(`test_csv.fillna(x.mean())`). 전처리 기준은 항상 train입니다(스케일러와 같은 원리).
- 경로 문자열 주의: `"c:\study\_data\ddarung\"`는 끝의 `\"`가 **따옴표를 이스케이프**하므로 문자열이 닫히지 않습니다. 결과는 `SyntaxError`입니다. `\n`, `\t`는 줄바꿈·탭으로 바뀝니다. 그래서 `/` 또는 `\\`, 또는 `r"..."`(raw string)을 씁니다.

### 2-2. 캐글 바이크 (`keras14_kaggle_bike1.py`)의 숨은 문제 3가지
```python
x = train_csv.drop(['casual','registered','count'], axis=1)   # (10886, 8)
x_train, x_test, y_train, y_test = train_test_split(x, y, test_size=0.7, random_state=55)
model.fit(x, y, epochs=100, batch_size=16)                     # ← x_train이 아니라 x 전체!
```
1. **`casual + registered = count`** 관계입니다. 이 둘을 피처로 두면 정답을 알려 주는 셈(**타깃 누수**)이고, test.csv에는 두 열이 없어 예측도 못 합니다. 그래서 drop합니다.
2. `test_size=0.7`이면 **train이 30%, test가 70%**입니다(의도는 아마 `train_size=0.7`).
3. `fit(x, y)`는 **test까지 포함한 전체**로 학습합니다. 그 뒤 `evaluate(x_test)`는 이미 본 데이터를 채점하는 셈이라 **점수가 실제보다 좋게** 나옵니다.
- 덤: 마지막 층이 linear라서 **음수 count**가 나올 수 있습니다. 이 대회 지표는 RMSLE(log 사용)라 음수 예측은 문제가 됩니다. 예측 후 `np.clip(y_submit, 0, None)`으로 막을 수 있습니다.
- `index_col=0`으로 `datetime`이 인덱스가 되어 x는 8열입니다.

### 2-3. 산탄데르 (`keras22`, 이진 / `keras24`, 다중 방식)
- 데이터: train `(200000, 202)`, 타깃 0:1 = **179902 : 20098 (약 9:1, 불균형)**
  - 전부 0이라고만 찍어도 **acc ≈ 0.90**입니다. 불균형 데이터에서 accuracy는 착시를 일으킵니다. 이 대회의 공식 지표는 **ROC-AUC**입니다.
  - 그래서 제출에는 `np.round` 전의 **확률값 그대로**가 유리합니다(AUC는 순위를 보는 지표라 0/1로 뭉개면 정보가 사라집니다).
- `keras22`의 버그: `x_test = test_csv`만 만들고 **`y_test`는 어디에도 없습니다**. 그래서 `model.evaluate(x_test, y_test)`에서 `NameError`가 납니다. test.csv에는 정답이 없으므로 평가는 `x_val, y_val`로 해야 합니다.
- `keras24`(이진 분류를 softmax 2개로 풀기)
  - `y = pd.get_dummies(y, dtype=int)`로 `(200000, 2)` DataFrame을 만듭니다.
  - `Dense(2, activation='softmax')`와 `categorical_crossentropy`를 씁니다.
  - 제출 전에는 `np.argmax(y_pred, axis=1)`로 0/1을 만듭니다(axis=1은 **행마다** 큰 열의 번호).
  - `sigmoid 1개 + BCE`와 `softmax 2개 + CCE`는 수학적으로 거의 같은 문제입니다. 파라미터 수만 마지막 층에서 조금 다릅니다.
  - 주석: Series는 `reshape`이 안 될 때가 있으므로 `y.to_numpy()` 또는 `np.array(y)`로 바꿉니다.

### 2-4. 시간 재기와 history (`keras18`, `keras19`)
- `start = time.time()` → `fit` → `end = time.time()` → `round(end-start, 2)`: **fit 구간만** 측정합니다.
- `hist = model.fit(...)` → `hist.history`는 `{'loss': [...], 'val_loss': [...]}` 형태의 **딕셔너리**입니다.
- `hist.history['loss'][2:]`: 처음 2 epoch는 loss가 너무 커서 그래프 스케일을 망치므로 **잘라내고** 그립니다.
- loss는 계속 내려가는데 val_loss가 올라가기 시작하면 **과적합**입니다. 그 지점을 자동으로 잡는 것이 `EarlyStopping`입니다.

## 3. 📏 평가지표와 출력층의 짝

| 문제 | 마지막 층 | loss | 예측 후처리 | 보조 지표 |
|---|---|---|---|---|
| 회귀 | `Dense(1)` (linear) | `mse` | 없음 | R2, RMSE |
| 이진 분류 | `Dense(1, 'sigmoid')` | `binary_crossentropy` | `np.round` (0.5 기준) | acc, (AUC) |
| 다중 분류 | `Dense(C, 'softmax')` | `categorical_crossentropy` (원핫 y) | `np.argmax(axis=1)` | acc |
| 다중 분류 | `Dense(C, 'softmax')` | `sparse_categorical_crossentropy` (정수 y) | `np.argmax(axis=1)` | acc |

- **R2** = `1 − SS_res / SS_tot` = `1 − MSE / Var(y)`
  - 1에 가까울수록 좋습니다. 평균만 찍는 모델은 0이고, 그보다 못하면 **음수**도 나옵니다.
  - TensorFlow에는 없으므로 `sklearn.metrics.r2_score`를 씁니다.
- **RMSE** = `√MSE`: **y와 같은 단위**라서 "평균적으로 몇 대(따릉이 수) 틀렸나"로 읽을 수 있습니다.
  - `root_mean_squared_error`가 sklearn 1.4부터 생겼고, 이전에는 `np.sqrt(mean_squared_error(...))`로 계산했습니다.
- sigmoid 오해 정정 (`keras21` 주석): "TF가 sigmoid 후 반올림한다"는 틀린 설명입니다.
  - `predict`는 **0~1 사이 확률**을 그대로 돌려줍니다. 그래서 코드에서도 `np.round`를 직접 합니다.
  - `metrics=['acc']`만 내부에서 **0.5 기준으로 판정**해서 정확도를 계산합니다. **loss(BCE)는 반올림 없이 확률로 계산**합니다.
- `keras21`의 `RMSE(y_test, y_pred)`는 분류에서는 의미가 약합니다. 0/1끼리의 RMSE는 `√(1−acc)`와 같습니다.
- `accuracy`는 미분할 수 없어서 **loss로는 학습할 수 없습니다.** 그래서 metrics로만 봅니다.

### 3-1. `stratify`와 `validation_split` 숫자 감각 (`keras21`)
- 유방암 데이터: 569개, 0:1 = 212 : 357. `train_size=0.7`이면 train 398개, test 171개입니다.
- `stratify=y`를 쓰면 test에도 비율이 유지되어 0이 약 **64개**(171 × 212/569 ≈ 63.7)입니다.
  - 코드 주석의 `test: 0이 53개, 1이 118개`는 **stratify 없이 돌렸을 때의 출력**으로 보입니다(비율 0.31, 원래 비율은 0.37).
- `validation_split=0.3`은 **x_train의 뒤쪽 30%**를 섞지 않고 잘라 val로 씁니다. 그래서 학습 278개, 검증 120개입니다.
  - `batch_size=32`이면 1 epoch에 `ceil(278/32)` = **9 step**입니다.

### 3-2. 기초 shape 문제 (`keras08`)
- `mlp3_1`: x `(10,3)`, y `(10,2)`이므로 `input_dim=3`, `Dense(2)`입니다. 예측 입력 `[[10,31,211]]`은 `(1,3)`이고, 목표값은 **11, 0**입니다.
- `mlp4`: x `(10,)`, y `(10,3)`이므로 `input_dim=1`, `Dense(3)`입니다. 목표값은 **11, 0, −1**입니다.
- `mlp1_1`에는 일부러 둔 듯한 **오타 3개**가 있습니다.
  - `epohcs=100`: Keras 3에서는 `TypeError`(알 수 없는 인자)입니다. 실행은 **여기서 먼저 멈춥니다.**
  - `model.predit`: `AttributeError`입니다.
  - `np.array[[6,11]]`: 함수에 대괄호를 썼으므로 `TypeError`입니다. 올바른 형태는 `np.array([[6,11]])`입니다.

## 4. 💬 프롬프트 설계 (`rag06`, `rag07`, `rag16`, `rag22_3`)

### 4-1. 기본기
- `rag06`: `llm.invoke('나는 누구게?')`에 LLM은 답할 수 없습니다. **호출 하나하나가 독립적이고 메모리가 없기** 때문입니다. 그래서 history를 직접 넣어 주거나 LangGraph 메모리(`InMemorySaver`)를 씁니다.
- `temperature=0`이면 가장 확률 높은 답 위주로 나와 **일관되게** 답합니다. 사실 기반 RAG에는 보통 0을 씁니다.
- `rag07`: `PromptTemplate.from_template("{country}의 수도는 어디인가요?")`
  - `print(prompt_template)`는 **템플릿 객체**를 보여 줄 뿐 아직 채워지지 않았습니다. `input_variables=['country']`로 나옵니다.
  - 채우려면 `prompt_template.format(country='한국')` 또는 `.invoke({'country':'한국'})`을 씁니다.
- 체인 약어 pmo/plp: **prompt → model(llm) → output parser**입니다.

### 4-2. `rag16`과 `rag22_3`의 프롬프트 비교
| | `rag16` | `rag22_3` |
|---|---|---|
| 형식 | `from_template` (문자열 하나) | `from_messages` (system / placeholder / human) |
| 변수 | `{context}`, `{input}` | `{context}`, `{chat_history}`, `{input}` |
| 규칙 | 없음 | 4가지 규칙, 특히 **"관련 정보가 없으면 '주어진 정보로 답변할 수 없습니다'"** |
| 기억 | 없음 | `history[-10:]`을 HumanMessage/AIMessage로 변환 |

- `create_stuff_documents_chain`이 검색된 문서를 **전부 이어 붙여(stuff)** `{context}`에 넣습니다. 변수 이름은 꼭 `context`여야 합니다.
- `create_retrieval_chain`의 입력 키는 꼭 `input`입니다. 결과는 `{'input', 'chat_history', 'context', 'answer'}`이고, `context`는 Document 리스트입니다.
- `history[-10:]`은 **최근 메시지 10개, 즉 사용자·봇 5턴**입니다. 프롬프트가 무한히 길어지는 것(토큰 비용 증가)을 막습니다.
- 규칙 4는 **환각 방지 장치**입니다. `score_threshold=0.7` 때문에 검색 결과가 0개일 수 있는데, 그때 아무 말이나 지어내지 않게 합니다.
- 한계: retriever에는 **`input`만** 들어갑니다. 그래서 "그거 더 자세히"처럼 대명사로 된 후속 질문은 검색이 엉뚱해집니다. history를 반영해 질문을 다시 쓰는 것이 `create_history_aware_retriever`의 역할입니다.

### 4-3. `rag22_3`의 임베딩·FAISS 함정
```python
######  임베딩 모델2: Qwen/Qwen3-Embedding-0.6B   ######
embeddings = HuggingFaceEmbeddings(model_name = "BAAI/bge-m3", ...)   # ← 실제로는 bge-m3
faiss_index = faiss.IndexFlatL2(len(embeddings.embed_query("hello world")))  # 주석: 1536
db = FAISS.from_documents(documents=pdf_split, embedding=embeddings)  # 매번 새로 임베딩
db = FAISS.load_local(..., index_name='faiss_index20_Qwen3-Embedding-0.6B', embeddings=embeddings, ...)
```
1. 제목은 Qwen3인데 **모델은 bge-m3**입니다. 불러오는 인덱스 이름은 Qwen3입니다.
   - 둘 다 **1024차원**이라 에러 없이 돌아갑니다. 하지만 **질문 벡터(bge-m3)와 문서 벡터(Qwen3)가 서로 다른 공간**에 있어 검색이 조용히 엉망이 됩니다.
   - 규칙: **저장할 때와 불러올 때 같은 임베딩 모델**을 써야 합니다.
2. 주석의 `1536`은 OpenAI `text-embedding-3-small` 기준입니다. bge-m3는 1024입니다. 그래서 `len(embed_query(...))`처럼 **직접 재는 방식**이 안전합니다.
3. `faiss_db`(빈 인덱스)를 만들고, `from_documents`로 다시 만들고, 결국 `load_local`로 **덮어씁니다.** 앞의 두 개는 매번 시간만 쓰고 버려집니다. PDF 전체를 매번 임베딩하므로 실행이 느립니다.
4. `allow_dangerous_deserialization=True`: FAISS 저장 파일(pickle)은 **불러올 때 코드가 실행될 수 있습니다.** **내가 만든 파일에만** 이 옵션을 켭니다.
5. `chunk_size=300`, `chunk_overlap=100`이고 overlap은 chunk_size보다 작아야 합니다. separators는 문단(`\n\n`) → 줄(`\n`) → 공백 → 글자 순으로 시도합니다.

<summary>C. 프롬프트 설계와 RAG</summary>

**C1.** `invoke` 호출은 하나하나가 **독립 요청**이고, LLM 자체에는 대화 기억이 없습니다. 해결 방법은 두 가지입니다.
1. 이전 대화를 메시지 리스트(Human/AIMessage)로 프롬프트에 직접 넣습니다(`MessagesPlaceholder`, rag21/22).
2. LangGraph의 `InMemorySaver` 체크포인터와 `thread_id`로 상태를 저장합니다(lg08).

**C2.** `['country']`입니다. 문장을 얻으려면 `prompt_template.format(country='한국')`을 쓰면 문자열이 나오고, `prompt_template.invoke({'country': '한국'})`을 쓰면 PromptValue가 나옵니다.

**C3.** 두 키는 다음과 같습니다.
- `"input"`: `create_retrieval_chain`이 이 키로 검색하고, 프롬프트의 `{input}`에도 들어갑니다.
- `"chat_history"`: 프롬프트의 `MessagesPlaceholder(variable_name='chat_history')`를 채웁니다.

`chat_history`를 빼면 프롬프트 변수가 채워지지 않아 **에러(누락된 입력 변수)**가 납니다.

**C4.** 메시지 16개 중 마지막 10개는 메시지 7~16번입니다. 이것은 **4번째 턴부터 8번째 턴까지(5턴)**입니다. 1~3턴은 잘립니다.

**C5.** 유사도 0.7 미만 문서는 검색에서 빠지므로, 문서와 무관한 질문이면 `context`가 **빈 리스트**일 수 있습니다. 규칙 4는 그때 LLM이 그럴듯한 답을 지어내지(환각) 않고 "답변할 수 없다"고 말하도록 막습니다. (일상 대화는 규칙 2로 허용합니다.)

**C6.** retriever에는 history 없이 **"그럼 decoder는?"만** 들어갑니다. 무엇의 decoder인지 정보가 없어서 검색이 부정확해집니다. 개선 방법은 `create_history_aware_retriever`입니다. LLM이 history를 보고 질문을 "Transformer의 decoder 층 수는?"처럼 **독립된 질문으로 다시 쓴 뒤** 검색합니다.

**C7.** 주석과 인덱스 이름은 Qwen3인데 실제 `HuggingFaceEmbeddings`는 **bge-m3**입니다. Qwen3 임베딩으로 저장된 FAISS 인덱스에 bge-m3로 만든 질문 벡터를 넣으면, **두 모델 모두 1024차원**이라 shape 에러가 나지 않습니다. 하지만 벡터 공간이 서로 달라서 검색 결과가 사실상 무작위가 됩니다. 저장과 불러오기에는 같은 모델을 써야 합니다.

**C8.** `faiss_db` 생성과 `FAISS.from_documents(...)`(PDF 전체 임베딩)가 매번 실행되지만, 결국 `load_local`로 덮어써져 버려집니다. 저장은 한 번만 하고(save 코드는 주석 처리), 실행 코드에서는 **`load_local`만** 남깁니다. 임베딩 모델 객체는 질문 임베딩에 필요하므로 유지합니다.

**C9.** FAISS의 docstore와 매핑 정보는 **pickle**로 저장됩니다. pickle은 불러오는 순간 임의의 파이썬 코드를 실행할 수 있습니다. 남이 준 파일이면 악성 코드가 실행될 수 있으므로, **직접 만든 파일에만** 이 옵션을 켭니다.
