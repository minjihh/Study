## 1. 핵심 정리

### 1-1. 도구 쓰는 챗봇 그래프의 뼈대 (lg07)
```
START ──► chatbot ──(tools_condition)──► tools ──┐
              ▲            │                     │
              │            └──► END              │
              └──────────────────────────────────┘
```
| 단계 | 코드 | 의미 |
|---|---|---|
| 도구 묶기 | `llm_with_tools = llm.bind_tools(tools)` | LLM에게 "이런 도구가 있어"라고 **스키마만 알려줌**. LLM이 도구를 직접 실행하지는 않음 |
| 상태 | `messages: Annotated[list, add_messages]` | 노드가 반환한 메시지를 **덮어쓰지 않고 이어 붙임**(리듀서) |
| 챗봇 노드 | `return {'messages': [llm_with_tools.invoke(state['messages'])]}` | 응답 `AIMessage`에 `tool_calls`가 있을 수도, 없을 수도 있음 |
| 도구 노드 | `add_node('tools', ToolNode(tools))` | 마지막 AIMessage의 `tool_calls`를 읽어 **실제로 도구를 실행**하고 `ToolMessage`를 돌려줌 |
| 조건 분기 | `add_conditional_edges('chatbot', tools_condition)` | 마지막 메시지에 `tool_calls` 있으면 `'tools'`, 없으면 `END`로 감 |
| 되돌아오기 | `add_edge('tools', 'chatbot')` | 검색 결과를 보고 LLM이 **다시 판단**(추가 검색 or 최종 답변) |

- `tools_condition`은 **`'tools'`라는 이름의 노드**로 보냄. 노드 이름을 `'tool'`이나 `'search'`로 바꾸면 라우팅이 깨짐. (이름을 바꾸려면 직접 라우팅 함수를 만들어야 함)
- `tools_condition`이 `END`를 반환할 수 있으므로 `add_edge('chatbot', END)`를 **따로 적지 않음** (코드 주석 그대로). 오히려 같이 적으면 도구 호출 때도 END로 가는 엣지가 생겨 흐름이 꼬임.
- `add_edge('tools','chatbot')`가 **루프**를 만든다는 점이 lg05(수동 구현)와의 핵심 차이. LLM은 여러 번 검색한 뒤 답할 수 있음.
- 실행 후 `response['messages']` 순서(도구 1번 호출 시):
  `HumanMessage → AIMessage(tool_calls) → ToolMessage(검색 결과) → AIMessage(최종 답변)`, 그래서 `[-1].content`가 최종 답변.

### 1-2. 그래프 그림 저장/출력 (lg07_01 vs lg07_02)
| | lg07_01 | lg07_02 |
|---|---|---|
| 데이터 | `png_data = graph.get_graph().draw_mermaid_png()` → **bytes** | 같음 |
| 처리 | `with open(path+'lg07_ToolNode.png','wb') as f: f.write(png_data)` | `Image.open(BytesIO(png_data))` → `plt.imshow(img)` |
| 결과 | 파일로 저장 (`./_save/image/` 폴더가 **미리 있어야** 함, 없으면 `FileNotFoundError`) | 화면에 바로 표시 (파일 안 만듦) |

- `'wb'`: bytes를 쓰므로 **바이너리 쓰기** 모드. `'w'`로 열면 `TypeError`.
- `with` 문 = `open` → 작업 → **자동 `close()`** (예외가 나도 닫힘).
- `BytesIO`: 메모리 속 bytes를 **파일처럼** 다루게 해줌 → `Image.open`이 파일 경로 대신 받을 수 있음.
- `draw_mermaid_png()`는 기본적으로 **mermaid.ink 웹 API**를 호출해서 그림을 받아오므로 인터넷이 필요함.

### 1-3. 검색 도구 교체: Tavily ↔ DuckDuckGo (lg06)
| | `TavilySearch(max_results=3)` | `DuckDuckGoSearchRun()` |
|---|---|---|
| 설치 | `pip install langchain-tavily` | `pip install -U ddgs` (+ `langchain_community`) |
| API 키 | **필요** (`TAVILY_API_KEY`, `.env`) | 불필요 (무료) |
| `invoke` 반환 | **dict**: `result['results'][i]['content']`로 접근 | **str** (검색 결과 요약 문자열) |
| 주의 | 유료/쿼터 | 여러 명이 동시에 쓰면 차단/DNS 에러 → 재시도 |

- lg06_01 주석 `print(result['results'][-1]['content']) #이거 키면 ... 에러남`이 바로 이 차이 때문. 문자열에 `['results']`를 하면 `TypeError: string indices must be integers`.
- 결과 개수 조절은 `DuckDuckGoSearchRun(api_wrapper=DuckDuckGoSearchAPIWrapper(max_results=5))`처럼 **wrapper에** 주는 게 정석. 코드에서 `DuckDuckGoSearchAPIWrapper`를 import만 하고 안 쓴 이유가 이것. `DuckDuckGoSearchRun(max_results=5)`처럼 바로 넘기면 반영되지 않을 가능성이 큼 (wrapper 기본값이 5라서 겉보기엔 차이가 없음).
- **도구 2개 동시 연결 (lg06_02)**: `tools = [web_search1, web_search2]` → `bind_tools`와 `ToolNode` **둘 다 같은 리스트**를 받아야 함. LLM은 도구의 `name`/`description`을 보고 고르고, ToolNode는 `tool_calls[i]['name']`으로 실제 도구를 찾음. 두 리스트가 다르면 "LLM은 부르는데 ToolNode엔 없는 도구" 에러가 남.
- 그래프 구조는 **한 글자도 안 바뀜** → 도구만 갈아끼우면 되는 게 LangGraph 구조의 장점.

### 1-4. 메모리(대화 기억): InMemorySaver + thread_id (lg08)
**Memory01 (기억 없음)**
```python
graph = graph_builder.compile()
graph.invoke({"messages": [("user", "내 이름은 허민지야")]})
graph.invoke({"messages": [("user", "내 이름이 뭐라고 했지?")]})   # → 모른다고 답함
```
- `invoke`마다 State가 **새로 시작**. 두 번째 호출의 messages에는 두 번째 질문 하나뿐.

**Memory02 (기억 있음): 3단계**
```python
from langgraph.checkpoint.memory import InMemorySaver      # ① import
memory = InMemorySaver()
graph = graph_builder.compile(checkpointer=memory)          # ② 컴파일 때 연결
config = {"configurable": {"thread_id": "user01"}}          # ③ 대화방 번호
graph.invoke({"messages": [...]}, config=config)
```
| 개념 | 설명 |
|---|---|
| checkpointer | 그래프가 **step마다 State 스냅샷을 저장**하는 저장소 |
| `thread_id` | 저장소 안의 **대화방 ID**. 같은 ID로 invoke하면 이전 State를 불러와 이어서 실행 |
| 이어 붙는 원리 | 불러온 이전 messages + 새 입력 messages가 **`add_messages` 리듀서로 합쳐짐** → LLM이 이전 대화를 다 봄 |
| 다른 `thread_id` | 완전히 새 대화 (이름 모름) |
| `InMemorySaver` | **파이썬 프로세스 메모리**에만 저장 → 스크립트 종료/재시작하면 사라짐. 영구 저장은 `SqliteSaver`, `PostgresSaver` 등 |
| 상태 확인 | `graph.get_state(config).values['messages']`로 저장된 대화 확인 가능 |

- config 모양이 **`{"configurable": {"thread_id": ...}}`** 로 한 번 더 감싸져 있다는 점 주의.
- checkpointer를 붙여 놓고 `config` 없이 invoke하면 → thread_id가 없다는 **에러**.
- 대화가 길어질수록 매 호출마다 **전체 messages가 LLM에 전달** → 토큰/비용 증가. (나중에 요약/잘라내기 필요)

### E (모범 답안 요지)
1. lg05는 "LLM → (tool_calls 있으면) 도구 1회 실행 → LLM"처럼 **정해진 순서**로 한 번만 처리. lg07은 `tools → chatbot` 엣지로 **루프**가 있어서, LLM이 결과를 보고 부족하면 또 tool_calls를 내고, 충분하면 tool_calls 없이 답해 `tools_condition`이 END로 보냄. 즉 **검색 횟수를 LLM이 스스로 결정**.
2. compile 시 checkpointer를 붙이면, invoke할 때 config의 thread_id로 저장된 마지막 State를 먼저 불러옴. 입력 `{"messages": [새 질문]}`은 State를 덮어쓰지 않고 `messages` 키의 리듀서 `add_messages`가 **기존 리스트 뒤에 추가**. 그래서 chatbot 노드의 `state['messages']`에 이전 대화 전체가 들어가 LLM이 기억하는 것처럼 보임. (리듀서가 없었다면 새 질문으로 **덮어써져** 기억이 사라짐)
3. ① 서버 재시작/배포 시 **모든 대화가 사라짐** ② 서버가 여러 대(프로세스 여러 개)면 **서로 메모리를 공유 못 함** ③ 대화가 계속 쌓여 **메모리 사용량 증가**. → `SqliteSaver`/`PostgresSaver` 같은 영구 저장소 + 오래된 대화 정리 필요.
