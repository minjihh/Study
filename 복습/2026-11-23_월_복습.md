## 1. 핵심 정리

### 1-1. feature_importances_ (m01_01, m01_02)
| 항목 | 내용 |
|---|---|
| 지원 모델 | `DecisionTree`, `RandomForest`, `GradientBoosting`, `XGB` 등 **트리 기반** 모델. 학습(`fit`) 후에만 존재(속성 끝의 `_`) |
| 모양 | `(n_features,)` → iris는 4개, diabetes는 10개 |
| 합계 | **1.0으로 정규화**되어 있음 |
| sklearn 트리 계산 방식 | 각 특성으로 분할할 때 줄어든 **불순도(지니/엔트로피, 회귀는 MSE)의 합** (MDI, Mean Decrease in Impurity) |
| `model.score()` | 분류기 → **accuracy**, 회귀기 → **R²** |
| `model.__class__.__name__` | 반복문 안에서 모델 이름을 문자열로 출력하는 방법 |

- `stratify=y`는 **분류에서만** 의미가 있음 (클래스 비율 유지). 회귀 타깃은 연속값이라 쓰면 안 됨 → m01_02(diabetes)에서 뺀 이유.
- 여러 모델을 리스트에 담고 `for model in models:`로 같은 흐름(fit → score → 중요도)을 반복하는 패턴.

### 1-2. XGBoost의 중요도 종류 (m01_03, m01_04)
| importance_type | 의미 | 어디서 기본값? |
|---|---|---|
| `weight` (= F score) | 그 특성이 **분할에 사용된 횟수** | `plot_importance()`의 기본값 |
| `gain` | 그 특성으로 분할했을 때 **손실함수 개선량의 평균** | XGB sklearn 래퍼 `feature_importances_`의 기본값(트리 부스터) |
| `cover` | 그 분할이 다룬 샘플 수(가중치) 평균 | — |
| `total_gain`, `total_cover` | 평균이 아닌 합계 | — |

- `model.get_booster().get_score(importance_type='gain')` → **dict** 반환, 키는 `'f0'`, `'f1'`… (numpy로 학습했기 때문에 컬럼명이 없음). **한 번도 분할에 쓰이지 않은 특성은 dict에서 빠짐.**
- `feature_importances_`는 정규화(합 1)된 **배열**, `get_score`는 정규화되지 않은 **원시 값**.
- ⚠️ 코드 주석 `# F스코어 : 빈도수` 는 `feature_importances_`에 대해 붙어 있지만, 최신 XGBoost에서 `feature_importances_`의 기본은 **gain(정규화)** 입니다. 빈도수(weight)를 보려면 `XGBClassifier(importance_type='weight')`로 만들거나 `get_score(importance_type='weight')`를 써야 합니다. (m01_02 sklearn 모델에 붙은 `# Frequency score` 주석도 실제로는 불순도 감소 기반)

### 1-3. LangGraph 병렬 실행 & 병합 (lg09)
```
START ──► search ──┐
   └────► analysis ─┴─► merge ──► END
```
- `add_edge(START, "search")` + `add_edge(START, "analysis")` → START에서 **두 갈래로 분기(fan-out)**. 두 노드는 같은 **super-step**에서 동시에 실행됨.
- `add_edge("search","merge")` + `add_edge("analysis","merge")` → 두 결과가 **merge로 모임(fan-in)**. 이번 구조는 두 갈래 길이가 같아서 merge가 다음 step에 **한 번** 실행됨.
  - 갈래 길이가 다르면 merge가 두 번 실행될 수 있음 → 확실히 "둘 다 끝난 뒤 한 번"을 원하면 `builder.add_edge(["search","analysis"], "merge")` 처럼 **리스트로** 연결.
- 병렬 노드들이 **서로 다른 키**(`search_result`, `analysis_result`)에 쓰기 때문에 충돌이 없음. 같은 키에 동시에 쓰려면 그 키에 **리듀서**(`Annotated[list, add_messages]`, `operator.add` 등)가 있어야 함. 없으면 `InvalidUpdateError`.
- 노드 함수는 State 전체가 아니라 **바꾸고 싶은 키만 dict로 반환**하면 됨.
- 세 파일의 차이

| 파일 | 입력 | search / analysis | merge 방식 |
|---|---|---|---|
| 병합1 | `{"question": ...}` | 하드코딩 문자열 | 문자열 이어 붙여 `final_result`에 저장 |
| 병합2_concat | `{"messages": [("user", q)]}` | Tavily 실검색 / LLM 분석 | 단순 concat → `messages`에 `("assistant", result)` 추가 |
| 병합3 | 동일 | 동일 | **LLM에게 두 결과를 프롬프트로 넘겨 종합** → `messages`에 AIMessage 추가 |

- `messages`는 `add_messages` 리듀서 → 반환한 메시지가 **덮어쓰기가 아니라 추가**됨. 그래서 최종 답은 `response["messages"][-1].content`.
- `("user", q)` 같은 튜플도 `add_messages`가 `HumanMessage`로 변환해 줌 → 노드에서 `.content` 접근 가능.
- `graph.get_graph().draw_mermaid_png()` → PNG **바이트** → `BytesIO`로 감싸 `PIL.Image.open` → `plt.imshow`.

<summary>E. 서술형 포인트</summary>

1. 바로 삭제는 위험. 중요도는 **그 모델·그 데이터 분할**에서의 값이라 random_state나 모델이 바뀌면 달라짐. 상관이 높은 두 특성은 트리가 둘 중 하나만 골라 써도 되므로 중요도가 **한쪽에 몰리거나 둘로 나뉘어** 각각 낮아 보일 수 있음. 삭제 후 성능을 직접 비교(교차검증)해서 판단해야 함.
2. 자주 분할에 쓰이지만 매번 손실을 **조금씩만** 줄이는 특성 — 예: 값의 종류가 많은 연속형/ID 같은 특성(고카디널리티), 노이즈에 가까운 특성. 실제 성능 기여는 gain이 더 잘 보여줌.
3. concat: LLM 호출 1회 절약 → 싸고 빠름, 원문 그대로라 왜곡 없음 / 대신 길고 정리 안 됨. LLM 종합: 읽기 좋은 하나의 답, 출처 구분 가능 / 호출 1회 추가(비용·지연), 환각·누락 가능성.
